我仔细过了一遍，**最值得动的不是算法本身，而是搬运、同步和日志**。这些地方提速空间很大，而且基本不碰效果。

我会把优先级排成这样：

1. **先砍掉每 iter 的强同步和重日志**  
   这是最稳的一刀。现在每 iter 都在做：
   - `loss.item()` 强同步 [train.py](/home/jian/gaussian-splatting/train.py#L419)
   - `max_memory_* / memory_*` 查询 [train.py](/home/jian/gaussian-splatting/train.py#L426)
   - `progress_bar.set_postfix()` + `update()` 每 iter [train.py](/home/jian/gaussian-splatting/train.py#L441)
   - `LOGGER.info()` 每 iter [train.py](/home/jian/gaussian-splatting/train.py#L448)
   - `reset_peak_memory_stats()` 每 iter [train.py](/home/jian/gaussian-splatting/train.py#L136)
   - 还有一段本质上是 debug 校验的 `vi.max().item()` [train.py](/home/jian/gaussian-splatting/train.py#L189)

   这类改动**完全不该影响指标**，但很可能白白吃掉一截吞吐。  
   我觉得这是第一优先，预计能拿回一块比较“干净”的速度。

2. **把 D2H 只缩到真正需要的 subset**  
   现在 `kick_async_d2h()` 会把整块 `n_vis` 的东西都搬回 CPU：[pipeline_grad_sync.py](/home/jian/gaussian-splatting/pipeline_grad_sync.py#L60)  
   但后面 `densify_stats` 实际只用：
   - `sub_vf` 选中的那一部分
   - `vpt_grad[..., :2]`
   - `radii[sub_vf]`  
   见 [pipeline_grad_sync.py](/home/jian/gaussian-splatting/pipeline_grad_sync.py#L127)

   也就是说现在很多 D2H 是“先全搬，再裁”。  
   这刀**不改训练语义**，但很可能是大头，尤其 visible points 高的时候。

3. **复用 GPU scratch，别每个 block 都临时分配**  
   当前 H2D 激活每次都：
   - `torch.empty(...)` 一个新的 `gpu_packed` [gaussian_model.py](/home/jian/gaussian-splatting/scene/gaussian_model.py#L1092)
   - 然后再切片/clone 六份属性 [gaussian_model.py](/home/jian/gaussian-splatting/scene/gaussian_model.py#L1097)

   D2H 这边也每次 `torch.cat(...)` 出一个新的 `gpu_grad_packed` [pipeline_grad_sync.py](/home/jian/gaussian-splatting/pipeline_grad_sync.py#L70)

   这类 allocator churn 很伤吞吐。  
   **预分配并复用 scratch buffer** 是纯工程提速，风险很低。

4. **当前每个 block 实际上做了两次 H2D/两次 render 路径**  
   一次 no-grad：[train.py](/home/jian/gaussian-splatting/train.py#L230)  
   一次 grad：[train.py](/home/jian/gaussian-splatting/train.py#L292)

   这件事是当前框架最大的结构性速度税。  
   但它比前面三刀更难，因为要在显存和复用之间折中。  
   我觉得可以作为第二波：**先缓存 1-2 个最热 block 的 GPU subset**，少做一部分重复 H2D。这个也不该影响效果，但实现会复杂一点。

5. **`empty_cache()` 现在触发得有点积极**  
   [train.py](/home/jian/gaussian-splatting/train.py#L414)  
   这会让 allocator 状态更抖。这个不影响结果，但我会放在前三刀之后再碰。

我反而**不建议**第一轮就动这些：

- `SKIP_SMALL_BLOCK_THRESH`
- 小覆盖块过滤
- frustum cache 提前复用
- 半精度
- 任何更激进的 block 跳过策略

这些虽然也可能加速，但已经开始碰效果边界了。你刚说的是“**不影响效果**”，那我们先别碰这条线。

所以如果按“投入产出比”排，我建议我们**先试这两组**：

- **A 组：日志/同步清理**
- **B 组：D2H subset 化 + scratch 复用**

这两组最像“速度明显变快，但指标不该动”。我下一步就先从这两组下手。
