# Faster 2 Plan

## Hard Constraints

- Do not increase training VRAM to gain speed.
- Do not keep extra GPU-resident caches across iterations or across blocks.
- Do not change training semantics in the first wave.
- Every step must be benchmarked against the same short run before moving on.

## Current Baseline

- Benchmark command: `bicycle / keep_training / 800 iter`
- Current code baseline: `7.92 it/s`
- Average memory: `alloc 0.27 GB / rsv 0.70 GB / peak 1.08 GB`
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` test:
  - `7.35 it/s`
  - `alloc 0.27 GB / rsv 0.45 GB / peak 1.08 GB`
  - Conclusion: reduces fragmentation, but slows this workload. Do not use as a speed path.

## Main Bottlenecks

- `densify_and_prune`: maintenance spike, about `265 ms / call`
- `packed_sparse_adam`: main steady-state CPU hotspot, about `4.9 ms / call`
- `h2d_grad`: about `2.7 ms / call`
- `h2d_nograd`: about `2.6 ms / call`
- `gather_nograd`: about `1.4 ms / call`
- Current grad path still does:
  - unpack one packed GPU buffer into 6 leaf tensors
  - then repack 6 grads back into one packed tensor for D2H

## Rejected Directions

- No extra `gpu_packed` cache
- No “keep hottest blocks on GPU”
- No GPU optimizer path that grows device state
- No full-GPU frustum-culling rewrite if it requires moving CPU-resident model state to GPU
- No half precision as a first-wave speed fix

## Execution Order

### Step 1: Remove Python-side per-iter overhead

Target files:

- [train.py](/home/jian/gaussian-splatting/train.py)

Planned changes:

- reduce per-iter `LOGGER.info`
- reduce per-iter `progress_bar.set_postfix`
- reduce per-iter `memory_*` queries
- reduce per-iter `reset_peak_memory_stats`
- guard or remove the visible-index debug `vi.max().item()` path outside debug mode
- keep benchmark accounting, but sample it sparsely enough to avoid turning it into the bottleneck

Why first:

- zero algorithm risk
- zero VRAM risk
- easy to measure cleanly

Acceptance:

- same memory envelope
- no change in training behavior
- measurable it/s gain on the short benchmark

### Step 2: Overlap CPU Adam with the next block’s GPU work

Target files:

- [pipeline_grad_sync.py](/home/jian/gaussian-splatting/pipeline_grad_sync.py)

Planned changes:

- move pending CPU Adam work onto a background thread
- keep GIL-free extension calls as the heavy work unit
- main thread continues scheduling next-block H2D/render while CPU Adam runs
- only synchronize when the next dependent stage truly needs the result

Why second:

- `packed_sparse_adam` is the largest steady-state hotspot
- this can cut wall time without changing semantics or VRAM

Acceptance:

- same memory envelope
- same optimizer semantics
- `packed_sparse_adam` time overlaps instead of stalling the main loop

### Step 3: Fix the packed grad path instead of unpack-then-repack

Target files:

- [scene/gaussian_model.py](/home/jian/gaussian-splatting/scene/gaussian_model.py)
- [pipeline_grad_sync.py](/home/jian/gaussian-splatting/pipeline_grad_sync.py)

Planned changes:

- keep one leaf `gpu_packed` tensor for the grad pass
- expose views into it for rendering instead of cloning six independent tensors
- after backward, copy `gpu_packed.grad` directly to pinned staging
- delete the current GPU-side `cat` repack path

Why third:

- removes unnecessary clone/repack overhead
- should not increase VRAM; may slightly reduce it

Acceptance:

- gradients numerically match the current path
- no extra persistent GPU memory
- reduced `h2d_grad` and D2H-side packing cost

### Step 4: Replace CPU gather with extension-side parallel gather

Target files:

- [scene/gaussian_model.py](/home/jian/gaussian-splatting/scene/gaussian_model.py)
- [submodules/diff-gaussian-rasterization/cpu_adam.cpp](/home/jian/gaussian-splatting/submodules/diff-gaussian-rasterization/cpu_adam.cpp)
- [submodules/diff-gaussian-rasterization/ext.cpp](/home/jian/gaussian-splatting/submodules/diff-gaussian-rasterization/ext.cpp)

Planned changes:

- add a packed-row gather helper in the extension
- use OpenMP parallel copy into pinned staging
- replace Python `torch.index_select(..., out=staging)` in `pre_gather()`

Why fourth:

- `gather_nograd` is now a visible steady-state cost
- this is a local engineering optimization, not a semantic change

Acceptance:

- same gathered data
- same memory envelope
- reduced `gather_nograd`

### Step 5: Trim maintenance spikes without changing densify semantics

Target files:

- [scene/gaussian_model.py](/home/jian/gaussian-splatting/scene/gaussian_model.py)
- [train.py](/home/jian/gaussian-splatting/train.py)

Planned changes:

- remove duplicate `empty_cache()` behavior from the hot maintenance path
- keep one cache-control policy, not two
- check if buffer reallocations after densify/prune can be batched or delayed safely

Why fifth:

- this is mainly about smoothing the catastrophic slow iterations
- higher risk than the previous steps, so do it after the low-risk wins

Acceptance:

- no VRAM growth
- no densify/prune behavior change
- smaller maintenance spikes

## Benchmark Rule

After each step:

1. run the same `bicycle / keep_training / 800 iter` benchmark
2. record `it/s`, `alloc`, `rsv`, `peak`
3. compare the new trace against the previous one
4. only continue if the step does not increase VRAM and actually helps

## Expected Outcome

- Step 1 + Step 2 should be the highest-confidence no-extra-VRAM wins
- Step 3 is the most promising structural cleanup
- Step 4 and Step 5 are follow-up optimization passes
- A realistic first target is a clear gain over `7.92 it/s` without raising VRAM
- Do not promise `2x` before Step 1-3 are finished and re-measured
