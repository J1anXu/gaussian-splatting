# Faster 2 Plan: `densify_and_prune`

## Goal

- Focus only on the maintenance spike around `densify_and_prune()`.
- Do not increase GPU memory to gain speed.
- Prefer structural cleanup over speculative threading.
- Benchmark every change against the same short run before keeping it.

## Current Judgment

`densify_and_prune()` is likely slow mainly because it rebuilds too much state, too many times, inside one maintenance call.

The first priority is **reduce copies / reduce full-state rebuilds / fix device mistakes**.
Only after that should we consider parallelism.

## Main Findings

### 1. CPU densify path still bounces through GPU

In [`scene/gaussian_model.py`](../../scene/gaussian_model.py), `densify_and_split(..., device="cpu")` still calls:

- `build_rotation(self._rotation[selected_pts_mask])` at line `685`
- then immediately `rots = rots.to(device)` at line `686`

But [`utils/general_utils.py`](../../utils/general_utils.py) hardcodes:

- `build_rotation()` output on `device='cuda'` at line `85`
- `build_scaling_rotation()` output on `device='cuda'` at line `104`

So for CPU maintenance we currently do:

- select on CPU
- build rotation on GPU
- move rotation back to CPU

This is not just suboptimal. It is very likely a real performance bug.

### 2. `split` is implemented as append-then-prune

Current flow in [`scene/gaussian_model.py`](../../scene/gaussian_model.py):

- `densify_and_split()` appends children through `densification_postfix()` at line `694`
- then immediately builds `prune_filter` and removes the original parents at lines `696-697`

This means one split operation does:

- full append of new tensors and optimizer state
- then full prune / slice of tensors and optimizer state

This is more expensive than necessary.

Reference from `GS-Scale`:

- [`gsplat/strategy/ops.py`](</home/jian/GS-Scale/gsplat/strategy/ops.py>) uses a one-pass `split()` that directly builds `[rest, children]`
- it does not append first and then prune the split parents as a second large mutation

### 3. One maintenance call performs multiple full parameter rebuilds

Inside one `densify_and_prune()` call in [`scene/gaussian_model.py`](../../scene/gaussian_model.py):

- `densify_and_clone()` may rebuild parameter tensors once
- `densify_and_split()` may rebuild parameter tensors again
- final `prune_points()` rebuilds them again

Relevant code:

- `_prune_optimizer()` lines `596-612`
- `cat_tensors_to_optimizer()` lines `631-651`
- `prune_points()` lines `614-628`
- `densification_postfix()` lines `653-671`

This suggests the spike is dominated by repeated whole-model mutation, not by a single expensive math kernel.

### 4. Stats are reset more than once per maintenance step

`densification_postfix()` resets:

- `xyz_gradient_accum`
- `denom`
- `max_radii2D`

at lines `669-671`.

Since `clone` and `split` can both call `densification_postfix()` in the same maintenance step, these full-size stats tensors can be reallocated and zeroed multiple times.

### 5. Packed Adam state does a heavy round-trip

Before densify:

- `_sync_packed_adam_to_optimizer_state()` at lines `858-878`

After densify / prune:

- `pack_to_buffer()` lines `779-818`
- `_init_packed_adam_state()` lines `880-909`

So the code currently does a packed-state to optimizer-state to packed-state round-trip during maintenance.

This is likely expensive in both memory traffic and pinned allocation churn.

### 6. Hot-path `empty_cache()` is still inside maintenance

`densify_and_prune()` ends with:

- `torch.cuda.empty_cache()` at line `735`

This may help peak memory occasionally, but it also makes maintenance spikes uglier and can increase allocator churn.

## What CLM-GS / GS-Scale Suggest

### From `CLM-GS`

`CLM-GS` does not have a magical parallel densify implementation. Its densify flow is still conceptually:

- accumulate stats
- clone
- split
- prune
- reset opacity

See:

- [`/home/jian/CLM-GS/densification.py`](</home/jian/CLM-GS/densification.py>)
- [`/home/jian/CLM-GS/strategies/base_gaussian_model.py`](</home/jian/CLM-GS/strategies/base_gaussian_model.py>)

What is useful from `CLM-GS` is not the densify algorithm itself, but the **preallocated pinned buffer** idea in `clm_offload`:

- [`/home/jian/CLM-GS/strategies/clm_offload/gaussian_model.py`](</home/jian/CLM-GS/strategies/clm_offload/gaussian_model.py>)

They reserve CPU pinned capacity and reuse it instead of allocating fresh pinned storage every time maintenance changes point count.

### From `GS-Scale`

The useful part is the mutation pattern in:

- [`/home/jian/GS-Scale/gsplat/strategy/ops.py`](</home/jian/GS-Scale/gsplat/strategy/ops.py>)

Especially:

- `duplicate()`
- `split()`
- `remove()`

The important idea is:

- build the new parameter/state layout in one pass
- avoid append-then-prune as two separate global rewrites

## Recommended Execution Order

### Step A: Fix the device bug in rotation helpers

Target files:

- [`utils/general_utils.py`](../../utils/general_utils.py)
- [`scene/gaussian_model.py`](../../scene/gaussian_model.py)

Planned changes:

- make `build_rotation()` allocate on `r.device`, not hardcoded CUDA
- make `build_scaling_rotation()` allocate on `s.device`
- remove the useless `.to(device)` bounce in CPU densify path if no longer needed

Why first:

- very low risk
- probably a real bug
- easy to benchmark

Acceptance:

- identical densify behavior
- lower maintenance time
- no VRAM increase

### Step B: Rewrite `densify_and_split()` as one-pass replacement

Target files:

- [`scene/gaussian_model.py`](../../scene/gaussian_model.py)

Planned changes:

- stop doing append children then prune parents
- instead build the final post-split tensors directly as:
  - untouched points
  - cloned points
  - split children
- mutate optimizer state once for split, not twice

Why second:

- this attacks the biggest structural waste directly
- inspired by `GS-Scale` split/remove ops

Acceptance:

- same final point set semantics
- fewer full tensor/state rewrites
- lower maintenance spike

### Step C: Collapse clone + split + prune into one maintenance rebuild

Target files:

- [`scene/gaussian_model.py`](../../scene/gaussian_model.py)

Planned changes:

- compute all masks first:
  - clone mask
  - split mask
  - prune mask
- do a single maintenance rebuild of:
  - parameter tensors
  - optimizer state
  - stats tensors
- reset `xyz_gradient_accum / denom / max_radii2D` only once per maintenance call

Why third:

- current code can rebuild the full model three times in one call
- this is the most promising structural cleanup after the device fix

Acceptance:

- same densify/prune semantics
- only one stats reset
- measurable maintenance reduction

### Step D: Reuse pinned capacity for maintenance-time buffers

Target files:

- [`scene/gaussian_model.py`](../../scene/gaussian_model.py)

Planned changes:

- add reusable CPU pinned capacity for:
  - `_packed`
  - `_packed_staging`
  - packed Adam state if applicable
- grow capacity only when needed
- avoid allocating fresh pinned buffers on every `pack_to_buffer()`

Why fourth:

- `CLM-GS` shows this pattern is practical
- maintenance currently changes point count often enough that pinned allocation churn matters

Acceptance:

- no extra GPU residency
- lower pinned allocation churn
- smoother maintenance latency

### Step E: Revisit cache policy in maintenance

Target files:

- [`scene/gaussian_model.py`](../../scene/gaussian_model.py)
- [`train.py`](../../train.py)

Planned changes:

- remove or relax `torch.cuda.empty_cache()` inside `densify_and_prune()`
- keep one cache policy, not separate hot-path and maintenance-path policies

Why fifth:

- allocator cleanup belongs after structural waste is removed
- otherwise it is hard to measure the real source of the spike

Acceptance:

- no VRAM growth beyond acceptable envelope
- reduced maintenance variance

## Parallelism: What Is Safe and What Is Not

### Not recommended first

- Do not parallelize inside one block’s `densify_and_prune()` immediately.
- `clone / split / prune / pack_to_buffer / optimizer.state` all mutate the same state.
- This is high complexity and likely memory-bandwidth bound.

### Potentially feasible later

- Parallelize maintenance across different blocks only after Steps A-C are done.
- A conservative version would use at most a small worker pool, e.g. 2-way concurrency.
- Maintenance for different blocks should only run after all dependent optimizer updates for the current iteration are complete.

## Rejected For Now

- no more async `densify_stats`
- no extra GPU caches
- no “hot blocks stay on GPU”
- no large-worker-thread rewrite inside the same block

## Benchmark Rule

For every accepted step:

1. run the same short `bicycle / keep_training` benchmark
2. record:
   - `it/s`
   - average `alloc`
   - average `rsv`
   - maintenance-time behavior from trace
3. reject the step if:
   - it raises VRAM
   - it changes training semantics unexpectedly
   - it does not reduce the maintenance spike enough to matter

## Current Recommendation

The best next move is:

1. fix the device bug in `build_rotation()` / `build_scaling_rotation()`
2. rewrite `densify_and_split()` so it no longer does append-then-prune

These two have the best chance of being both correct and worth keeping.
